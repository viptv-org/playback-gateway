## Dependency changes versus candidate v1.61.0

A source diff from candidate revision `486bcbe758e0cff0f750fcee9c26268a11250d77` to reference dependency `d913b30f520e10e85a94c7dc4b7b3e828b22c4b2` shows meaningful changes, but **does not fix capped-storage Reader cancellation recursion**. `readAt` still retries after resetting its storage reader/completion state, then recursively calls itself on any remaining error when storage is capped. It has no terminal `ctx.Err()` check before that recursion. `waitAvailable` returns cancellation errors, which can consequently feed repeated retries instead of unwinding. The newer mutex around the reader context field fixes a data race, a separate issue. [Reader retry/cancellation](https://github.com/anacrolix/torrent/blob/d913b30f520e10e85a94c7dc4b7b3e828b22c4b2/reader.go#L310-L360), [context synchronization commit](https://github.com/anacrolix/torrent/commit/3e9eb41b10c47b32b369f84a641470ded8aec802).

Other relevant differences:

- File-scoped reads now clip the buffer to the file extent, protecting adjacent-file byte boundaries. [Extent fix](https://github.com/anacrolix/torrent/commit/142076b1d51c4dc88fb1dabb022b96936980ab4c).
- `StealRequestGrace` can prevent very young requests being stolen/cancelled repeatedly. Its default remains0, and the inspected Go reference does not explicitly set it; a dependency upgrade alone therefore does not enable a grace policy. [Grace implementation](https://github.com/anacrolix/torrent/commit/23d8abf909ada242ec2e883cb49d2a230cf4a795), [default](https://github.com/anacrolix/torrent/blob/d913b30f520e10e85a94c7dc4b7b3e828b22c4b2/steal-request-grace.go#L5-L18).
- Tracker-input updates are batched and indexed overdue handling changes; consecutive announce failures now back off from1minute toward30minutes. The failure backoff operates after unsuccessful announces, so does not establish better initial cold acquisition. [Dispatcher source](https://github.com/anacrolix/torrent/blob/d913b30f520e10e85a94c7dc4b7b3e828b22c4b2/client-tracker-announcer.go), [backoff commit](https://github.com/anacrolix/torrent/commit/4aea1d64b31783c3e77f5e927955260bad6ddf54).
- Peer-ranking keys are cached, and per-piece/request-state allocations and hash-worker shutdown change. These can affect CPU/RAM and retirement; their effect on first-frame/sustained decode still requires measurement. [Ranking commit](https://github.com/anacrolix/torrent/commit/8592293b0df8f557352012d2246d33062cebb8db), [closed hash-worker check](https://github.com/anacrolix/torrent/blob/d913b30f520e10e85a94c7dc4b7b3e828b22c4b2/torrent.go#L2810-L2828).

A future pinned-version comparison must first reproduce bounded-reader cancellation and byte-boundary tests. It must retain the candidate's cancellation workaround; do not adopt this dependency as a cancellation fix. An explicit nonzero request-grace sweep is a separate scheduling experiment, with wasted/cancelled blocks and decoder-current-piece age measured alongside latency.

## Discovery and connection scheduling

The client enables both IP families, TCP/uTP, DHT, PEX, seeding, webseeds and optionally WebTorrent. Default peer budgets are50established/25half-open/500queued; encryption defaults remain MSE-preferred. Its `disable` encryption option actually sets `Preferred=false, RequirePreferred=false`, permitting encrypted fallback rather than enforcing plaintext-only, despite the adjacent comment. There is no explicit fast-dial rate/deadline override in client construction. [Client configuration](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L288-L377), [peer budget and encryption](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L2267-L2300).

It merges caller/metainfo trackers and always adds a baseline public list, including when caller trackers exist. Candidate defaults are added only when the source has no tracker hints. Tracker initialization synchronously loads a saved ranked list, then optionally refreshes in the background every24hours. Ranking keeps5UDP/HTTP trackers by default after a successful refresh; the initial embedded fallback has11UDP plus3WSS entries and is not itself truncated to5. WSS entries are merged separately. [Admission](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L531-L554), [merging](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1940-L1974), [inventory and refresh](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/trackers.go#L31-L240).

The ranking probe measures UDP connect-handshake RTT or HTTP HEAD/GET completion, with concurrency32 and1s/2s deadlines. It does **not** measure a successful announce for the requested torrent or the usefulness of returned peers. Reducing trackers is an experiment in CPU/discovery overhead and coverage, not established startup acceleration. [Ranking and probes](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/trackers.go#L260-L413).

## Verified read scheduling

The streaming path uses ordinary `torrent.File.NewReader` with readahead and never calls `SetResponsive` in the inspected checkout ([dependency Reader source](https://github.com/anacrolix/torrent/blob/d913b30f520e10e85a94c7dc4b7b3e828b22c4b2/reader.go#L103-L143)). It preserves the ordinary reader verification gate; it is not the official JavaScript server's virtual-chunk-before-original-piece-verification path. Opening a stream also calls `File.Download`, allowing the whole selected file to download while the reader exists; the last reader's close demotes the file and releases its boundary priorities. Candidate demand instead covers current readers and bounded lookahead. [Reader construction](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1232-L1280), [file selection](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L133-L186), [close](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1549-L1608).

Useful mechanisms:

- Readahead starts at8MiB, grows to twice sampled bytes/second, caps at64MiB, and is recomputed every3s. The speed input comes from engine statistics. Candidate currently defaults to32MiB, capped by a fraction of its cache. [Adaptive window](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1448-L1471), [updates](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1610-L1624).
- Boundary priority uses4MiBhead/8MiBtail rounded to pieces, rather than a fixed8piece count. The latter wording survives in an older function comment, but the executed constants/math are byte based. Candidate priming presently demands one byte at each end, fetching the containing pieces. [Boundary windows](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L2029-L2078), [applied priority](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L2107-L2142).
- A dedicated tail reader drains8MiB with a2minute timeout. A small leading MP4 box inspection skips this drain when `moov` precedes `mdat`. This skip applies to tail draining; unconditional boundary priming can still request tail pieces. It additionally primes the next video file's boundary at Normal priority, introducing consumer selection outside the candidate's exact-file scope. [Tail reader/detection](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1281-L1430), [next-file prefetch](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L1626-L1668).

## Cache limits and reuse

Default storage is infohash-partitioned file storage. Eviction measures allocated blocks on supported Unix platforms, waits90sgrace, then removes idle whole torrents. It protects open readers and always preserves the most recently used torrent in positive-budget eviction. A single large active or most-recent torrent can therefore exceed the configured cache budget. This is not a strict rolling piece store. [Storage selection](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L326-L345), [eviction](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L900-L1025), [allocated-size measurement](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/diskusage_unix.go#L15-L34).

Optional RAM storage exposes one shared request-capacity function across torrents and evicts complete pieces by last-read recency. First writes allocate whole-piece buffers after attempting eviction; if no complete victim exists, allocation proceeds above capacity. Evicted-read handling schedules `Piece.VerifyData` to invalidate stale engine state and trigger refetch. It demonstrates a refetch seam but cannot replace the candidate's strict charge/reservation bound, retained disk cache or current-piece protection. [RAM capacity and eviction](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/memstorage.go#L139-L237), [allocation/completion](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/memstorage.go#L291-L424), [refetch](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/engine/engine.go#L248-L282).

## RAR behavior

The inspected archive API accepts HTTP(S) or confined local paths. HTTP archives are fully downloaded to a temp file before listing/selecting a member, capped at4GiB. Multiple HTTP parts are downloaded and concatenated into one temp file; this is not a seekable torrent-backed RAR-volume filesystem. The selected member is then fully extracted into a second temp file, cached per session with single-flight extraction, and only afterward served with `http.ServeContent` Range support. Declared extracted size is capped at64GiB; those per-file checks do not establish one aggregate archive+torrent cache bound. [Download/parts](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/api/archive.go#L644-L724), [create](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/api/archive.go#L894-L1004), [extraction](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/api/archive.go#L749-L858), [serving](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/api/archive.go#L1100-L1133).

Its RAR wrapper reopens a sequential rardecode reader and walks entries; it exposes only `io.ReadCloser`. Unlike the candidate's `rardecode.FileSystem(torrentFS)` stored-member reader, this API does not map member seeks directly onto verified torrent volume ranges. It therefore supplies no ready-made replacement for stored multipart RAR startup. [RAR wrapper](https://github.com/M0Rf30/stremio-server-go/blob/cd0ab97f6fdaaa28eff447cfdfbfdb3adc3714ed/internal/archive/archive.go#L261-L343), [candidate archive contract](../torrent-runtime/archive.go).

## Candidate experiments

Keep current network tuning, verification policy, exact-file authority and strict cache accounting fixed; test each change separately on fresh and retained caches.

1. Compare current32MiBreadahead with8MiBinitial lookahead growing toward2sthroughput, always inside the existing cache admission bound. Measure first verified bytes/frame, decoder-blocking request age, seek recovery and sustained stalls; a faster first frame with later stalls is not an improvement.
2. Compare one-piece head/tail demand with4MiBhead/8MiBtail windows. For8MiBpieces these windows often resolve to the same one-piece boundaries, so confirm actual piece counts before interpreting the result. Record which extra piece requests compete with the decoder's current piece. Do not copy next-file prefetch or background full-file downloading.
3. On confirmed faststart MP4, compare tail priming enabled/disabled. Keep the fallback for unknown layouts and measure first-frame latency plus tail/seek recovery. Non-faststart MP4 and MKV remain separate cohorts.
4. After fixing regular-tracker timing instrumentation, compare the current20endpoint inventory with a5endpoint subset selected by successful useful announces, not RTT alone. Do this in an owned fixture first; live coverage and stale rankings require independent qualification. No automatic public probing/remote inventory refresh is proposed for production.
5. The prior audit's dual-stack fast/prime + plaintext-first and separate TCP-only experiments remain the direct tests of handshake/transport ordering. This repository mostly retains upstream defaults and provides no measured evidence that it solves those delays.

This audit supplies mechanisms to test, not evidence of better playback performance or authorization for production adoption. Existing [runtime research](TORRENT_RUNTIME_RESEARCH.md) and the candidate's cache/selection contracts remain authoritative.

## Follow-up: supported integrity comparison

The inspected official server bundle (download v4.21.1, runtime v4.21.0) implements a per-engine creation option through its existing API:

```http
POST /<requested-infohash>/create
Content-Type: application/json

{"virtual":false}
```

This is an **implemented shipped API option**, not a documented user-facing settings switch. The route passes the entire JSON body to `createEngine`, which overlays it on the defaults; false therefore overrides the application's `virtual:true`. Public [enginefs source at9f11922ae092e4a7120a7e1bdabb0698df1eecb8](https://github.com/Stremio/enginefs/blob/9f11922ae092e4a7120a7e1bdabb0698df1eecb8/enginefs.js#L357-L363) preserves that route, and its [creation code](https://github.com/Stremio/enginefs/blob/9f11922ae092e4a7120a7e1bdabb0698df1eecb8/enginefs.js#L70-L98) forwards engine options. Context7 resolution returned no enginefs documentation; the mechanism was established from public/shipped source and the controlled test below.

Use a fresh process and private state, and make this the **first** creation request for the torrent. Engines are reused when already present; later create requests update reported options without rebuilding the engine, so `stats.opts.virtual=false` alone would not prove an existing engine changed mode. The separate `/create` route with `from`/`blob` constructs only `{torrent: parsed}` and discards other caller options; it cannot carry this override. Sources in the recorded [official bundle](/tmp/viptv-torrent-reference-research/stremio-official-v4.21.1/server.js:18114): overlay/reuse18114–18125, hash-create route18356–18361, metainfo-create route18383–18405. [Official download](https://dl.strem.io/server/v4.21.1/desktop/server.js); recorded provenance remains under `/tmp/viptv-torrent-reference-research/stremio-official-v4.21.1/provenance.json`.

With virtual disabled, the engine retains the original piece length and SHA1 map. `store.verify` synchronously hashes the full original piece; a hash failure clears availability before the file-stream notification can run. Virtual mode instead has512KiBavailability units whose original hash can remain incomplete. Source: [piece initialization](/tmp/viptv-torrent-reference-research/stremio-official-v4.21.1/server.js:72467), [download/verify/reset ordering](/tmp/viptv-torrent-reference-research/stremio-official-v4.21.1/server.js:72568), [synchronous storage verification](/tmp/viptv-torrent-reference-research/stremio-official-v4.21.1/server.js:74603), [file reader availability gate](/tmp/viptv-torrent-reference-research/stremio-official-v4.21.1/server.js:74745). No official bundle modification was used.

### Owned corrupt-piece proof

An additional controlled fixture ran in a fresh unshared user/network namespace with only loopback enabled, using an owned synthetic tracker/seeder and fresh private APP_PATH per arm. The synthetic single-file torrent has one2MiBoriginal piece. The seeder first supplies every16KiBblock but corrupts byte0, then withholds any valid replacement until the observation window ends. A64KiBHTTP range starts at byte0. The fixture is arbitrary generated bytes, not a decodable movie; all numeric timing is fixture-local and supplies no public-swarm speed qualification.

| Observation | Official per-engine `virtual:false` | Official ordinary default (virtual omitted) |
| --- | ---: | ---: |
| Runtime version |4.21.0|4.21.0|
| Observed `opts.virtual` |false|true|
| Original piece length |2,097,152B|2,097,152B|
| Corrupt payload supplied before valid release |2,097,152B|2,097,152B|
| Media bytes exposed before valid release |0|65,536B|
| Delivered corrupt first byte |no|yes|
| Recovery after valid original piece supplied |65,536B, exact match|not needed for positive control|

In the verified arm, the server's downloaded counter reached2,097,152B, all128distinct request offsets were served, and media remained at0bytes for750.085ms after corrupt-piece receipt. After releasing valid data, the same owned seeder supplied a complete valid piece and the HTTP206 reader returned the exact65,536byte range without error; local release-to-read completion was6.694ms. Persisted metainfo independently retained original piece length2,097,152B. A preliminary run also passed; the recorded final run deliberately **omitted** virtual from the control request rather than explicitly settingtrue.

Numeric evidence: [verified-piece-fixture-proof.json](/tmp/viptv-torrent-reference-research/verified-piece-fixture-proof.json). Harness: [verified_piece_fixture.py](/tmp/viptv-torrent-reference-research/verified_piece_fixture.py), launched with the existing `run_isolated.sh`. Neither output contains source identities, URLs or peer addresses. This proves the tested mode rejects a corrupt complete original piece and recovers for this owned2MiBfixture. It does not qualify every cache mode, restart state, piece size, multi-file boundary, cancellation path or public torrent. Candidate verification policy was not changed.

Keep the unchanged-default official reference as a separate arm. A fresh official `{virtual:false}` arm can now compare original-piece verification on the tested creation path; its public-swarm performance remains unmeasured by this follow-up. Neither the controlled proof nor an integrity-aligned comparison alone passes the candidate's relative startup or sustained-playback gates.

### Go reference benchmark path

M0Rf30's pinned revision already uses whole-piece-gated anacrolix readers; there is no need to request `virtual:false`, and its typed create body has no such field.

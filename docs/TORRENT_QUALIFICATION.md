# Torrent/archive qualification

The transport is an opt-in local implementation, not a deployed backend/client
cutover. BitTorrent v1 uses scoped librqbit sessions and one global cache budget;
metainfo and direct stored archives retain the vetted HTTP egress seam. Runtime
support defaults off. HTTP trackers are stripped; private tracker torrents and
webseeds are refused. These are deliberate supported-subset limits, documented
because the pinned library lacks a vetted tracker client and webseed support.

## Byte transport and lifecycle

Deterministic host fixtures use a local BitTorrent TCP seeder, never the public
network. They verify largest-media/explicit selection, middle/suffix Range,
HEAD, 416 handling, token rejection, stable sharing within a namespace,
different namespace URLs, explicit stop, idle eviction and cache locking.
An HTTP tracker listener proves tracker metadata is not contacted. Metainfo
stripping preserves the exact raw info dictionary and original piece hashes.

Control fixtures verify runtime-off refusal before source activity, private
HTTP denial, direct stored-RAR ranges and source lifetime. Pending source
admission is registered before source I/O and promoted atomically into the
output ledger. Concurrent distinct inputs cannot spend the same key slot.
Canceled blocking extraction retains its global reservation and key admission
until actual completion; quota and byte-capacity regressions cover that case.
An output retains its input through actual worker/read teardown.

Full-storage mode reserves logical torrent payload size before download, plus
declared compressed-member spool size before extraction. Rolling mode reserves
fixed piece slots for non-archive inputs larger than the per-input budget;
see [rolling cache implementation and checks](ROLLING_TORRENT_CACHE.md).
Active input reservations cannot be evicted; server reaping removes fully idle
inputs promptly. Rolling mode evicts individual pieces within an active input.
Filesystem metadata/block rounding remains outside the logical budget. Use the
supplied cache tmpfs or an equivalent independent filesystem limit for a kernel bound.

## Real media

Ignored host FFmpeg fixtures verify two viewers and a late viewer share one
HLS output, a separate VOD seek decodes a frame matching source time 3 seconds
rather than time zero, and final release reclaims input/output reservations.
Generated stored four-volume RAR media verifies shared HLS and seeking without
a spool copy. Compressed RAR verifies one complete checksum-verified spool,
byte identity with the generated source, shared output and seeking after
extraction. Fixture bytes and commands live in engine/assets/rar-media.

Run with real binary paths and one test thread:

```sh
CARGO_BUILD_JOBS=2 PLAYBACK_TEST_FFMPEG=/usr/bin/ffmpeg \
  PLAYBACK_TEST_FFPROBE=/usr/bin/ffprobe cargo test -p playback-gateway --lib \
  workers::torrent_tests::real_torrent_viewers_share_output_seek_and_reap_owned_input \
  -- --ignored --exact --test-threads=1
```

`scripts/check-torrent-container.sh IMAGE all` archives the committed source,
builds its Workers library fixtures, and executes them with the selected fresh
image's FFmpeg/ffprobe. Each test runs once as UID10001 with network none,
read-only root, no capabilities, two CPUs and bounded memory. The modes are
`torrent`, `rolling-torrent`, `stored-rar`, `compressed-rar`, `bounded-archive`, and `egress`. The bounded mode
uses an actual 2 MiB archive-cache tmpfs and checks preparation ENOSPC,
`processing_failed`, partial-spool removal and recovery. It does not qualify
failure of a previously ready viewer or the public service binary's API paths.
The egress mode verifies a selected playlist cannot reach a private HTTP child;
its generated byte root is authorized by exact URI while normal destination
validation protects nested requests. It also verifies nonstandard MP4 playlist
refusal on the qualified FFprobe version.

All five modes pass. Hosts requiring sudo for Docker must provide a PATH-visible
wrapper so `timeout` can invoke it; exporting a shell function alone does not
cover that child executable.

The inherited progressive/runtime/CBR4K/bounded-media fixture builders include
the new ffi workspace member so they remain reproducible from Git archives.
The five required inherited progressive modes (`matroska`, `matroska-tls`,
`bounded-matroska`, `ts`, `bounded`) also pass; see
[progressive live delivery qualification](PROGRESSIVE_QUALIFICATION.md) for their
separate live-media scope.

## Native library

UniFFI host tests use the same local-seeder boundary and verify file selection,
byte seeking, progress callback and explicit stop. The four Android ABIs build
with verified ELF LOAD alignment of at least 16 KiB. This is compilation and
host-native evidence; APK ZIP alignment, Media3 consumption, devices and store
release are separate. The facade serves torrent payload bytes and currently
does not unpack archives. See ffi/README.md.

## Remaining acceptance

Actual service-binary HTTP qualification now proves runtime-off refusal before
source I/O/cache creation, runtime-on selected metadata, shared viewers/late join,
decoded three-second VOD seek, scoped control/media authorization, source-identity
redaction, renewal and final admission reclamation. Run
`bash scripts/check-torrent-api-container.sh IMAGE` for the four exact fixtures.
They use locally generated media and a deterministic BEP 3 peer, never public
peers. The enabled driver requires NET_ADMIN only inside its guarded network-none
namespace; that mode does not qualify production UID10001 containment. The
disabled fixture runs as UID10001 with no capabilities. VOD seek origins reserve
separate input/output slots even though torrent payload storage is shared.

Additional actual-binary fixtures now prove ready-viewer cache exhaustion and
one deliberate crash/restart. The cache case decodes real HTTP HLS before a
2-MiB tmpfs reaches ENOSPC, observes `failed/processing_failed`, denies media,
reclaims admission and decodes a fresh source after pressure removal in the same
process. The crash case kills a ready owner with an active media child, observes
interrupted transport and settled child/peer/locks, then restarts the same data
directory, rejects old viewers, retains its scoped key and decodes fresh media.

A further cold-cache trusted-HTTPS browser fixture passes with a browser client's
WebCodecs/canvas decoder. It proves a decoded three-second seek, normal 20-second
renewal, old/final release and complete admission reclamation. The actual
gateway child runs as UID10001 with no effective capabilities and NoNewPrivs.
Its privileged network-none setup driver remains
separate from a fully unprivileged production container.

The generated 120-second 320x180 H.264/AAC source transfers 4,397,700 bytes through
one deterministic peer over 21,795 ms. Active cache is observed, then the default
service reaper evicts it and stops the peer after final cleanup while readiness
remains healthy. `Sources::new` deliberately uses zero idle timeout for the
service; the engine library's 60-second default is a different policy. The test
changes neither. Run `scripts/check-torrent-browser.sh` with the runtime image, a
built `tv-web` checkout (archived; used only as the browser test page) and the
trusted local certificate directory.

The product/backend account, catalog and approved Source boundary is mocked;
actual service/media/decoder paths are real. Installed/native playback, Media3,
physical devices, multi-peer or hour-long sustained workloads, and repeated
crash/stress workloads remain separate acceptance gates.
The generic gateway's existing FFmpeg/media response failures retain their
separate qualification; those results do not substitute for torrent-specific
ready-viewer failure evidence. GPL distribution restrictions remain recorded
in PROVENANCE.md. No production data, deployment or migration is involved.

[Client integration and remaining qualification](https://github.com/viptv-org/playback-gateway/issues/15)
tracks the follow-up contract, actual service/API and trusted-HTTPS clients,
Android packaging/player behavior, ready-viewer failure and sustained/crash work.
It does not qualify those paths or authorize a production cutover.

The standalone browser fixture also accepts the test-only environment option
`PLAYBACK_TEST_DUAL_AUDIO=true`: it generates two explicitly mapped silent AAC
inputs, tagged eng/spa and titled English/Spanish. This provides deterministic
managed-track media for native qualification without audible tone inputs. Exact
image FFprobe checks observe three streams (H.264 plus two tagged AAC); fmt,
strict all-target Clippy and default workspace tests pass. That generation check
does not qualify native selection, managed replacement or physical audio. The
ordinary single-audio browser fixture remains unchanged.

## Controlled magnet bootstrap and bounded peer workloads

The opt-in browser driver now supports `PLAYBACK_TEST_MAGNET=true` and
`PLAYBACK_TEST_SWARM_PEERS=1..4`. Generated infoHash/fileIdx inputs are approved
by the real backend; actual service metadata resolves through controlled BEP 5
DHT and BEP 10/BEP 9 peers, then standard BEP 3 payload requests. The metadata
bytes are the exact generated info dictionary, not a preloaded service input.
The container's default DHT bootstrap names map to the guarded public-class
loopback alias only inside Docker `--network none`; production flags and address
policy are unchanged. No public torrent or public DHT is contacted.

A one-peer real backend/browser case passed in 51.99 seconds: 4,990 metadata
bytes, 16 DHT get_peers queries and 4,014,795 payload bytes over 19,996ms.
A three-advertised-peer case passed in 63.03 seconds with two actual payload
contributors: 9,980 metadata bytes, 18 DHT queries and 4,014,631 payload bytes
over 25,863ms. A separate fresh three-peer process cycle passed in 44.0 seconds
with all three peers contributing, 9,980 metadata bytes, 14 DHT queries and
6,832,456 delivered payload bytes over 34,664ms. Delivered byte counts include
repeated block requests and do not mean unique downloaded bytes.

Each case used the same qualified runtime image, actual UID10001 service, real
backend-approved Source, trusted HTTPS, decoded three-second browser seek,
renewals/releases and two-input/two-output/four-viewer reclamation. Active
cache payloads were removed and peer transports settled before owned shutdown.
These are bounded fresh-process cases, not a long-duration public swarm, a
universal peer compatibility or adverse Internet traffic claim.

Protocol references: [BEP 5](https://www.bittorrent.org/beps/bep_0005.html),
[BEP 9](https://www.bittorrent.org/beps/bep_0009.html) and
[BEP 10](https://www.bittorrent.org/beps/bep_0010.html).
